# Revisão do site e Área do Cliente — 20/10/2026

## Estrutura e escopo

Site estático com 27 páginas HTML na raiz. `css/v6.css` agrega estilos; `css/jss/v6-app.js` implementa autenticação e fluxos ativos do cliente. O frontend administrativo usa scripts separados. `sw.js` e os dois manifests definem o PWA. `io/` e `android-app/` são aplicações separadas. A suíte contém 23 verificadores Python e testes Node do Service Worker.

Revisão feita a partir de `main`, em branch separada. Nenhuma alteração em produção, DNS, CNAME, Cloudflare, dados, políticas ou configuração Supabase. Nenhuma alteração em paleta, fontes, logotipos ou estrutura das páginas.

## Problemas corrigidos

- **Área do Cliente:** `FormData` era criado depois de desabilitar os campos, excluindo seus valores. Agora a coleta ocorre antes do bloqueio; um sinalizador impede envio duplo durante a autenticação e o insert; `finally` libera os controles mesmo após erro de rede. Dados antigos com descrição nula deixam de interromper a listagem.
- **Desempenho:** a listagem deixa de pedir todas as colunas, incluindo mensagens e projeto completos; mantém os campos usados nos cards e contadores e o filtro de proprietário.
- **Segurança/PWA:** cache de recursos restrito a caminhos explícitos de arquivos públicos existentes. Requisições com Authorization, caminhos desconhecidos, recursos de `/io/`, queries não reconhecidas e respostas redirecionadas não entram no cache. Rotas autenticadas e Supabase continuam excluídos.
- **PWA:** busca em caches próprios, priorizando HTML atualizado sobre o shell de instalação. Arquivos de versões diferentes não se substituem no fallback offline. Falha ao gravar cache não descarta uma resposta de rede válida. Versão do cache incrementada para invalidar o cache anterior.
- **Responsividade:** textos longos em títulos, mensagens, descrição e anexos podem quebrar linha; itens flex/grid podem encolher sem alterar o desenho dos cards.
- **CI:** o workflow existente passa a executar também os testes de comportamento do cliente.

A lista `PUBLIC_ASSET_PATHS` precisa incluir novos recursos públicos que devam funcionar offline. Um recurso fora da lista continua sendo carregado normalmente pela rede.

## Validação

- 23 scripts Python passaram.
- 19 testes Node passaram: dados de formulário, envio duplo, falhas, visitante sem sessão, filtros de proprietário, fronteiras do cache, versões offline, prioridades, redirecionamentos e falha de gravação.
- `node --check` passou em 20 arquivos JavaScript (`css/jss/*.js` e `sw.js`).
- `git diff --check` passou.
- Testes de cliente usam um backend fictício em memória; não provam isolamento RLS do banco real.
- Validação visual em Chromium não concluída: executável ausente e download do navegador retornou arquivo inválido. Não foram medidos Core Web Vitals ou feitas afirmações de ganho numérico de desempenho.

## Pendências para homologação

1. Validar em 360, 390, 768 e 1366 px: home, serviços, nova solicitação, painel e detalhe. Usar títulos, mensagens e nomes de arquivos longos. Conferir teclado, foco, menus e zoom.
2. Em ambiente autorizado, criar uma solicitação com todos os campos; repetir com conexão interrompida e duplo clique. Confirmar conteúdo salvo e ausência de duplicação no fluxo normal. O bloqueio de envio é local à página, não idempotência no servidor.
3. Testar login/logout, recuperação de senha e isolamento entre clientes A/B, incluindo anexos e ações administrativas, no projeto Supabase confirmado. Frontend não substitui RLS.
4. Revisar políticas, grants, funções, bucket privado e MFA no backend correto. Esta revisão não acessou nem alterou esses recursos.
5. Verificar headers HTTP efetivos: `_headers` é configuração declarativa e não comprova aplicação pelo GitHub Pages/proxy.
6. Homologar instalação e atualização do PWA em Android/iOS, offline público e acesso online às páginas privadas; preservar identidades distintas cliente/ADM.
7. Chat ainda usa atualização de um array de mensagens: envios simultâneos podem se sobrepor. Uma solução definitiva requer operação atômica no backend e autorização específica para sua alteração.
8. Listagens ainda dependem do limite de linhas da API. Paginação e contadores globais precisam ser tratados juntos em uma próxima mudança, para não apresentar totais parciais como completos.

## Rollback

Reverter o commit do PR. Se a versão chegar a ser publicada futuramente, incrementar novamente `VERSION` do Service Worker no rollback, para que dispositivos removam o cache da versão revertida. Não há migração de banco a desfazer.
